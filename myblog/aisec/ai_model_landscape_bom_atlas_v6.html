How the hub is organised

Four modalities, one pipeline tag each

In plain English

Hugging Face is a website where people upload finished AI models so others can download and use them. An app store, except the apps are trained models.

There are about three million, far too many to browse. Every upload carries a tag saying what job it does. That tag is how you find anything. Below are the four big families of jobs.

Every repository carries a pipeline tag naming the task the model performs. That tag is the real browsing index for a three-million-repo population — not the model name, and not the vendor.

Why this matters for a bill of materials

The pipeline tag is the closest thing the Hub has to a declared purpose, and purpose is what EU AI Act Annex IV asks for. A model card that omits the tag omits the one field an assessor reaches for first.

What a model repository actually contains

  • README.md — the model card. YAML front matter carries licence, base model, datasets, language and pipeline tag. Everything below is free prose and is not machine-readable.
  • config.json — architecture, hidden size, layer count, vocabulary size. Reliable, because the loader depends on it.
  • Weight files — .safetensors (safe to load) or .bin / .pt (pickle, executes code on load). A control finding, not a preference.
  • Per-file SHA-256 and a commit SHA via the Hub API. Pin the commit SHA — a model ID without a revision is a bookmark, not an inventory entry.

Named models, owners, adopters, BOMs

Model catalog

In plain English

Forty real models. Click any column heading to sort by it. Tick "Concise table" at the top to strip it down to the essentials.

Owner is the legal entity that controls the model and the country whose laws they answer to. Known adopters lists companies that have publicly said they use it — almost every row is empty, and that emptiness is real, not laziness. Licence is the rulebook: green use freely, pink cannot sell, yellow get a lawyer, grey subscription only.

The BOMs button on each row opens a ready-made ingredients label for that model, which you can download.

On the adopters column, before you read it

There is no telemetry anywhere that links companies to models. This column contains only cases where a company or the model's owner has said so publicly, on the record. Two of forty rows are populated — Llama and Mistral, the two families whose vendors actively publish customer names. The other thirty-eight are not gaps in the research; they are the actual state of disclosure, and a client deck claiming otherwise has invented its data.

Note too that disclosures name a family, not a version. A bank that announced Llama 2 in 2024 is not evidence about Llama 4 today.

Columns Views

Reading the cost and deployment columns

Cost to use separates two things people routinely conflate. Every open-weight model is free to download. Only some are free to ship in a product. A green badge means you can put it in a commercial product; pink means you can prototype but not sell; amber means the owner wrote conditions you need read; purple means you rent it by the token and never hold the weights.

Runs where is the honest hardware floor, not the vendor's claim. Several families span a size ladder — the badge reflects the variant most teams actually deploy, and the note says so where the range is wide. Frontier open-weight models are nominally local and practically data-centre, which is why quantised GGUF conversions carry most of their real traffic.

Hosting routes matters for jurisdiction. Self-hosting puts the weights inside your boundary. Using the owner's own API does not — and for the PRC-domiciled models that is a materially different legal position from downloading the same weights.

What the generated BOMs are, and are not

Each row produces a CycloneDX 1.6 skeleton built from what this catalog knows: the model identity, its owning entity, jurisdiction, licence, task, access model, and any export-control or corporate-status flag. Jurisdiction and regulatory standing are carried as custom properties, because neither CycloneDX nor SPDX defines a native field for them.

A skeleton is a starting artifact, not an assessment record. It cannot know your pinned commit SHA, your resolved dependency versions, your accelerator inventory, or the training-data disclosure the upstream owner never wrote. Every skeleton ships with an explicit gap list naming what it could not fill. Run the OWASP AIBOM Generator or cdxgen against the live model to complete it, then merge.

The security read

The counted charts say the same thing from different angles: the model your engineers actually pulled into production is small, obscure, and several fine-tunes downstream of a base nobody documented. It is not the frontier model in the press release. Any AIBOM programme that inventories only the named flagship models will miss almost all of the real exposure.

Standards and tooling

BOM libraries by layer

In plain English

A bill of materials is an ingredients label. When a flaw is found in one ingredient, everyone searches their labels and knows in minutes whether they're affected.

An AI system has five kinds of ingredient and no single label covers them all. Code is one list. The model and its training data are a second. The chips are a third. The encryption is a fourth. The outside services are a fifth. The middle three are far less mature than the first.

There is no single BOM that covers an AI system. There are five overlapping ones. The useful question is which layer a given tool can actually see.

SBOM

Software bill of materials

Covers packages, libraries, frameworks, versions, transitive dependencies, container layers.

Standards CycloneDX (OWASP) and SPDX 3.0 (Linux Foundation, ISO-standardised).

Tooling Syft, cdxgen, Trivy, Microsoft sbom-tool, sbom4python, Amazon Inspector SBOM Generator. Dependency-Track for continuous consumption. Protobom and bomctl translate between formats.

Regulatory hook FDA §524B for cyber devices. The practice survived the partial rollback of US Executive Order 14028 and is now a standard procurement term.

AIBOM

AI / ML bill of materials

Covers models, weights, base-model lineage, training and evaluation datasets, hyperparameters, hardware requirements, governance metadata. Also called AI SBOM, ML-BOM, or SBOM for AI.

Standards CycloneDX ML-BOM and the SPDX 3.0 AI Profile plus Dataset Profile. Generate CycloneDX internally where tooling matters; require SPDX 3.0 from vendors where regulatory weight matters.

Tooling OWASP AIBOM Generator (model ID in, CycloneDX 1.6 plus a completeness score out); cdxgen with the aibom alias, which also reads Modelfiles, GGUF artifacts and MCP configs; ALOHA; AIBoMGen-cli and its GitHub Action.

Known gap neither format carries native fields for bias assessment, human-oversight design, owner jurisdiction or regulatory standing. Those stay as custom properties — which is exactly what the per-model skeletons in the catalog tab do.

HBOM

Hardware bill of materials

Covers physical components, silicon, boards, firmware-bearing parts, country of origin, supplier tiering.

Standards the CISA ICT SCRM Task Force HBOM Framework, which defines use-case-driven attribute sets rather than one fixed schema. CycloneDX represents hardware through the device component type. IPC-1752A and IPC-1754 cover materials declaration.

Maturity the weakest of the five. Most HBOM production is still spreadsheet and ERP extract rather than pipeline-generated.

Where it bites for AI accelerator provenance and firmware. If the model runs on an inference card, that card has its own supply chain, vulnerability stream and export-control posture.

CBOM

Cryptography bill of materials

Covers algorithms, key lengths, certificates, protocols and cryptographic library dependencies.

Standards CycloneDX added first-class cryptographic asset support from 1.6.

Tooling cdxgen, plus tracebom which profiles a running application and captures negotiated TLS suites and dynamically resolved crypto libraries.

Driver post-quantum migration. You cannot schedule an algorithm replacement across an estate you have not inventoried.

SaaSBOM / OBOM

Service and operations bills of materials

SaaSBOM covers external services, endpoints, data flows and trust boundaries — where an agentic system's tool calls and MCP servers live. CycloneDX defines the services schema. This is also where a hosted model endpoint's jurisdiction becomes recordable.

OBOM covers the running host: installed packages, configuration drift, persistence mechanisms. cdxgen ships an obom mode for Linux, Windows and macOS.

Why both matter for an agent runtime, the model file is a minority of the attack surface. Prompts, tools, retrieval sources, guardrails and MCP configurations are the rest.

VEX

Companion artifact

A BOM tells you what is present. A Vulnerability Exploitability eXchange document tells you whether a vulnerability in a listed component is actually exploitable in your product. Formats: CSAF VEX, OpenVEX, CycloneDX VEX.

Without VEX, an SBOM published to customers generates a support queue rather than assurance — every downstream scanner flags every CVE in every listed dependency.

Read before use

Caveats

In plain English

Download counts include robots. Licences change without warning. Owners change too. Two surveys are never comparable. Nobody publishes which company runs which model, so the adopters column is nearly empty on purpose. And the generated BOMs are starting drafts, not finished records.

What is counted

  • All Hugging Face repository counts, download shares and derivative counts come from Hugging Face's own State of Open Models reporting for January–August 2026 and its model statistics blog. Platform telemetry, not survey estimates.
  • Download counts are unfiltered and include bot and CI traffic. A relative signal between models, not a count of humans.
  • Parameter-count analysis covers only models that declare a parameter count.

What is asked, and what is simply absent

  • Industry and sector figures are survey-reported adoption rates with different definitions, denominators and sampling frames. Do not compute differences between bars from different sources.
  • There is no published dataset mapping models to industries, and no telemetry mapping models to companies. The adopters column carries only on-the-record public statements.
  • Disclosures name a model family and a point in time. Treat them as existence proofs, not as current-state inventory.
  • Survey panels are confidential, so there is no company-level roster behind the adoption or agent charts.
  • The multimodal modality share is a derived remainder, not a reported figure.

What changes fastest

  • Model licences. A model can be relicensed, and derivatives frequently misstate the base model's terms. Verify against the live card and the base model's card.
  • Owner standing. Entity List designations are added and removed, companies are acquired or wound up, names change. The two flagged entries were verified in August 2026 and should be rechecked against the BIS Entity List before any procurement decision.
  • OpenAI model availability. IDs retire on published sunset schedules, and ChatGPT retirements do not always coincide with API retirements.
  • EU AI Act dates. The AI Omnibus of 27 July 2026 moved Annex III high-risk obligations to 2 December 2027 and product-embedded high-risk AI to 2 August 2028. The dates moved; the inventory requirement did not.

Suggested workflow

  • Enumerate every model reference in the codebase, including those loaded by string at runtime, then resolve each to a commit SHA.
  • Download the skeleton from this tool as a starting frame, then run the OWASP AIBOM Generator or cdxgen against the live model and merge the resolved fields in.
  • Record owning entity and jurisdiction as custom properties. Neither CycloneDX nor SPDX has a native field.
  • Separate weight downloads from hosted-API calls in the inventory. Different legal acts, different exposure.
  • Merge the AIBOM with the application SBOM, add the SaaSBOM for tool and MCP surfaces, hold the HBOM separately if the workload runs on dedicated accelerators.
  • Regenerate on every commit. A bill of materials produced once is stale the day it is signed.
