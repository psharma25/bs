2 · Run a Single Attack ▾

Pick an attack and press Run once. Because defenses are probabilistic, the same attack can be blocked on one run and slip through on another — run it a few times.

3 · Automated Campaign Monte Carlo▾

Fire every attack many times and measure Attack Success Rate with 95% Wilson confidence intervals. This is why real red-teaming runs hundreds of trials: model behavior is probabilistic, so a single run tells you almost nothing — the distribution does.

4 · Defense Layers ▾

Each layer has a detection rate (probability it catches a covered attack on a given trial) — real detectors are imperfect. Fuzz mutations lower the effective rate. Toggle layers, then re-run the campaign to watch ASR move.

5 · Detector Accuracy & Metrics▾

Evaluate an input detector against a labeled corpus (malicious + benign look-alikes) — the real precision/recall tradeoff of text-based filtering.

12 · Overlap — where the three tools meet▾

There is overlap, and it clusters where you'd expect. All three test the LLM01 core (prompt injection + jailbreaks); they diverge by layer and workflow. The shared centre is "everyone covers this, redundantly"; the outer crescents are "only this tool gives you this".

garak — raw model sweep PyRIT — programmable campaigns Promptfoo — CI/CD app testing
Why they overlap: the shared centre exists because prompt injection and jailbreaks are the LLM01 core every tool must cover — the redundancy is a feature (three independent tools confirming one bypass raises confidence). The reason to run all three is the crescents: garak gives breadth, PyRIT gives multi-turn depth a single-shot scan misses, and Promptfoo turns findings into release-blocking regression tests. Using one tool alone leaves a specific, predictable blind spot.

13 · Guardrails — where they sit in the request path▾

Runtime filters placed at distinct control points around the model. No single point can perfectly filter free-flow text, so production systems layer them — each rail catches a different vector, and the output rail runs independently of the prompt path so a compromised model cannot talk its way past it.

Why layered, not a single filter: a text classifier on input alone is bypassed by encoding, indirect injection, and multi-turn escalation — vectors that never appear in the literal user message. Rails at input, source, output, tool, and dialog each cover what the others miss, and the output rail is the backstop: because it inspects the response rather than the prompt, an injection that fools every upstream layer still can't exfiltrate a secret it can't get past the output scan. Honest limit: guardrails reduce risk, they don't eliminate it — pair them with least-privilege tooling and rotate any secret that ever reaches an output.

15 · Detecting, deciding & learning in real time▾

A guardrail scores every prompt instantly and routes it. The hard part is the doubt band: if you ask the person "did you really mean this?", an attacker just says yes. So you never let the actor self-certify — you verify something they can't fake.

Learning in real time (the feedback loop)

Poisoning caveat: learn only from confirmed labels — human review, a labeled canary set, or a real incident. Never learn from the system's own automated guesses: an attacker who sees "it let X through" can feed it more X until the learner trusts the attack.
The principle: authenticate the authority to cause the effect, don't interrogate the intent of the text. Intent is fakeable; an approval from a different person, or a permission the session doesn't hold, is not.

16 · How to build a RAG chatbot▾

RAG = Retrieval-Augmented Generation. Rather than hoping the model memorized your data, you retrieve the right snippets from your own documents and hand them to the model with the question. Two pipelines: one prepares the data ahead of time, one runs on every question.

Why teams choose RAG: answers come from your current documents, you can show citations, you update knowledge by re-indexing instead of retraining, and private data stays in your store. The rails map onto it: source rail on ingestion, input/output rails on the query path, authorization gate if the bot can act.

The build spectrum

Plain LLM→ add your data → RAG→ add tools/actions → Agentic Pick the least powerful one that answers the need — every step up adds attack surface.

17 · How companies typically use LLMs / RAG▾

Most enterprise use clusters into a few patterns. The badge shows what's under the hood: plain LLM just the model, RAG model + your data, agentic model + tools/actions.

Where the volume is: the biggest three in most companies are the internal knowledge assistant, the customer-support assistant, and coding assistants — the first two almost always RAG, because the value is answering from the company's own current, private data with citations. Agentic use grows fastest and carries the most risk, which is why the authorization gate matters most there.
