CONTINUOUS, INTEGRATED, ENVIRONMENT-AWARE SECURITY

Feedback loops, not gates — security runs in the flow of engineering, not next to it
Feedback loop:Every finding updates the threat model, the paved-road template, and the test suite — so the same defect class cannot be introduced the same way twice. Two mechanics do most of the work: ratchet, don't gate (block only on new criticals in changed code, never on the backlog), and exceptions that expire (named business risk owner, expiry date, stated compensating control).

The enablers that make it real

Eight capabilities. None of them is a new class of tool — they are the same tools moved off the calendar and onto the commit.

Long-lasting components — the 10 to 20 year problem6,15,16

Most DevSecOps material assumes what you shipped can be re-shipped. In medtech, industrial, and embedded, that assumption fails.

Declare

Support horizon recorded at component selection, not discovered at end of life. The failure mode is not the vulnerability — it is discovering in year nine that nobody chose year nine.

Contain

What cannot be patched gets isolated: no network reachability, no untrusted input, a mediating process with a small verified interface. Architecture-level containment outlives any patch cadence.

Answer

Machine-generated VEX published on a schedule turns a support-ticket burden into a build artifact. For a fielded product, the recurring cost is not fixing — it is responding.

Survey

Postmarket surveillance as a running control, not an annual review. Watch list wired to KEV and vendor advisories, routed through coordinated disclosure with defined human decision points.

Re-platform

A ten-year product needs two or three planned toolchain migrations. Teams that don't fund them do an unplanned one under breach pressure, with the original engineers gone.

Managed libraries — SCA done right6,10,15

THE REGISTRY IS THE CONTROL
  • Curated internal registry; approved versions resolve by default
  • Version allow and deny policy enforced at build, not at review
  • SBOM produced as a build artifact, never as a report
  • Automated upgrade pull requests with test-gated merge for patch versions
RANK, DON'T CLOSE
  • 84.2% of SCA alerts sit on dependencies the application never calls10
  • Only 2.1% of alerts were potentially executable in the same study10
  • But dynamic analysis caught vulnerable code executing that static analysis called unused
  • Reachability sets the order of work. It does not retire a finding.

Where AI actually helps — and where it does not3,9

AI is good at high-volume, low-judgment work. It is not the accountable party.

THREAT MODELING
  • Derives data flows and trust boundary changes from a diff
  • Proposes candidate threats; the engineer confirms or discards
  • Keeps the model current between human reviews
CODE AND TESTS
  • Generates from governed templates, not from open prompts
  • Writes the regression test for each confirmed threat
  • 85% of AI-generated code failed controlled XSS tests9
TRIAGE
  • Deduplicates across SAST, SCA, DAST, and pentest into one finding
  • Correlates findings into attack paths
  • Drafts the remediation; a human merges it
NOT THIS
  • No model sets a risk acceptance
  • No model closes a finding on its own judgment
  • No model signs a release for a regulated product
  • Those carry names, and the name is the point

Measure what matters9,14

Risk reduction, speed, and friction — not activity. Scans run and reviews completed are attendance metrics. Put these beside your DORA delivery metrics rather than instead of them: if remediation latency falls while lead time rises, you relocated friction rather than removing it.

Two to watch:Recurrence rate is the honesty check on the whole model — escape rate and vulnerable age improve when you buy better tooling; recurrence only falls when a finding actually updated the model, the template, and the tests. Remediation latency is the closest direct reading of the queue, and the number most leaders cannot produce on request.
