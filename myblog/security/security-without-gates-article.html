Product security

Security Without the Gates

How to build controls engineers don't work around

One

The problem: we find vulnerabilities too late, and it costs too much

Every product security program I have inherited had the same artifact somewhere in it: a review nobody skipped, attached to a decision nobody remembered making. An architecture review board that approved a design six months before the code shipped. A threat model in a shared drive describing a system since rewritten twice.

People did the work. The work stopped mattering the moment the thing it governed changed.

Research on defect origins has been consistent for three decades. Most defects are introduced early — roughly 70 to 80 percent in requirements, architecture, and code.1 Fixing in production runs 50 to 100 times more expensive than fixing in requirements.7

And the gap between those two facts is widening. The 2026 Verizon DBIR found vulnerability exploitation became the leading initial access vector for the first time in the report's nineteen-year history, at 31 percent of breaches, while only 26 percent of CISA Known Exploited Vulnerabilities were fully remediated.8 Veracode's 2026 data puts average fix time at 252 days, up from 171 five years ago.9

Attackers moved to the front door. The front door takes longer to close than it did five years ago.

Friction is what connects the two. Late involvement, big-bang reviews, manual processes, unclear ownership, tool sprawl. Every one of those is a queue, and every queue is something we scheduled.

We need a different model: continuous, integrated, environment-aware, and automation-first.

Where bugs, cost, and friction originate

Understanding this is the first step to fixing it. Three views of the same eight phases.

Read those three rows top to bottom and the argument writes itself.

A requirements defect is not intrinsically expensive. It becomes expensive because design decisions, code, tests, and eventually deployed instances got built on top of it while nobody was looking. Cost is a function of delay.

Now look at the red row again. Not one entry is a missing tool. Every single one is a wait.

The queue is the control.Whatever your scanners find, your actual exposure is set by the interval between a defect being created and an engineer hearing about it. If you have never measured that interval, you do not know what your control is set to.

This is also why shift-left as commonly practiced fails. It moves the review earlier without removing the wait, producing an earlier bottleneck instead of a later one. What has to move left is feedback latency, not calendar position.

Three

The continuous, no-gates security model

Security runs in the flow of engineering, not next to it. Same eight phases, now with what replaces the gate.

Two mechanics in that grid do more work than the rest combined.

Ratchet, don't gate. Blocking applies only to new critical findings in changed code. Nobody has to fix the backlog to ship — they just cannot make it worse. A gate that surfaces four thousand findings teaches exactly one skill, which is how to bypass the gate.

Exceptions that expire. Time-bound, with a named business risk owner and a stated compensating control. Exceptions the security team owns never close, because nobody in the business is waiting for them to.

Four

The enablers that make it real

None of these is a new class of tool. They are the same tools moved off the calendar and onto the commit.

Integrated and environment-aware threat modeling

Model the whole system once and store it as code in the repository. After that every model is a diff, triggered by a change to a trust boundary, a data flow, a privileged operation, or an external integration. The engineer reviews three threats, not ninety.

Environment-awareness matters as much as integration. The same code carries different threats in a hospital VLAN, a customer VPC, and a device on a home network — so deployment context has to be a variable inside the model rather than an assumption sitting outside it.3,5

AI-assisted secure code generation

The value is not speed. It is that the paved road becomes the path of least resistance. Two conditions attach: the templates are the security control and get reviewed as such, and generated code is tested by the same suite as hand-written code. Without a governed template library, generation increases defect potential — Veracode's 2026 data found 85 percent of AI-generated code failing controlled cross-site scripting tests.9

Continuous SAST, DAST, secrets, and IAST

Incremental against the diff, in the IDE and the pull request, under five minutes. Full scans nightly, never blocking.

Managed libraries and SBOM-driven SCA

Software composition analysis is a registry problem, not a scanner problem. Curate an internal registry where approved versions resolve by default, enforce the allow and deny policy at build rather than at review, and produce the SBOM as a build artifact.6,15

Then use reachability to rank, not to close. One study found 84.2 percent of SCA alerts sat on dependencies the application never called, and only 2.1 percent were potentially executable. The same study also found cases where dynamic analysis observed vulnerable code executing that static analysis had marked entirely unused.10 Reachability sets the order of work. It does not retire a finding.

Auto-testing at every stage

Every surviving threat produces a security regression test. If a threat cannot be expressed as a test, either it is not real or it is not yet understood.

Attack-graph-driven prioritization

Four thousand findings is not four thousand risks; it is perhaps thirty paths. Correlate exposure, reachability, privilege, and impact into paths, then fix the choke points — which are usually an exposure or a privilege rather than a code change.

Continuous remediation and learning

Fix at the source, not the instance. If forty services carry the same vulnerable library, the fix is the base image, not forty tickets. Set SLAs by exploitability rather than CVSS alone: KEV-listed and reachable in days, reachable with high EPSS in weeks, everything else on the next scheduled upgrade cycle.

And be honest about the arithmetic. 252 days to fix half your flaws is a capacity problem, not a discipline problem, and capacity is a budget decision. Debt burn-down needs a funded program, not slack-time goodwill.

Five

The part nobody writes about: components that outlive the toolchain

Most DevSecOps material assumes what you shipped can be re-shipped. In medtech, industrial, and embedded, that assumption fails. A device fielded in 2026 is supported into the 2040s. The toolchain is frozen. The OS is a vendor BSP with no upstream. A patch may require regulatory action.

Declare the support horizon at component selection, not at end of life. When a component's horizon is shorter than the product's fielded life — which for most runtimes and kernel branches it always is — that gap becomes a recorded design decision with a funded re-platform date. The failure mode is not the vulnerability. It is discovering in year nine that nobody chose year nine.

Contain what cannot be patched. Move the control from the component to its boundary: no network reachability, no untrusted input, a mediating process with a small verified interface. Architecture-level containment is durable in a way a patch cadence is not.

Let VEX do the answering. For a fielded product with a thousand-component SBOM, the recurring cost is not fixing, it is responding. Machine-generated VEX statements published on a schedule convert a support burden into a build artifact.15

Treat postmarket surveillance as a running control. Under FD&C Act §524B the obligation is continuous.16 Wire the watch list to advisories, route through a coordinated disclosure pipeline with defined human decision points, and let the evidence accumulate.

I took an infusion pump through 510(k) clearance while the submission sat under an FDA Regulatory Hold. The lesson that transferred was not about the submission. It was that the only evidence worth having is the evidence the process already generates — because when a regulator asks, reconstructing it is not an option, and there is no calendar left to try.

Budget re-platforming as maintenance. A ten-year product needs two or three planned toolchain migrations. Teams that do not fund them do an unplanned one under breach pressure, with the original engineers gone.

Six

Measure what matters

Focus on risk reduction, speed, and friction — not activity. Scans run and reviews completed are attendance metrics; they tell you the program showed up, not that it worked.

Two of the six deserve special attention.

Recurrence rate is the honesty check on the entire model. Escape rate and vulnerable age can improve simply because you bought better tooling. Recurrence only falls when a finding actually updated the threat model, the paved-road template, and the test suite. If everything else improves and recurrence holds flat, you built faster detection, not a feedback loop.

Remediation latency is the number most leaders cannot produce on request, and it is the closest thing you have to a direct reading of the queue. Measure it and you will find your control setting.

Seven

The outcome

One honest trade. You give up veto points. Things will ship that you would have paused, and some will be wrong. You spend more engineering effort upfront — writing an adversarial test suite is more work than attending a review. And you accept residual risk explicitly, in writing, with a named business owner. That last one is where most programs flinch: if every exception still routes back to security for a real decision, you kept the gate and added paperwork.

Some things should stay gates. Gate the irreversible and the legally attributable: a premarket submission, production access to patient data, the first deployment of an agent with write authority into a system of record. And no model sets a risk acceptance, closes a finding, or signs a regulated release — those carry names, and the name is the point.

Most programs have this exactly backwards. They gate the routine, where volume guarantees a workaround, and automate the exceptional, where a human decision would have been worth the wait.

If you change one thing this quarter, measure your queues. Put your own numbers on the friction row above. You will not need to argue for anything after that.

Security without the gates means context, automation, feedback, and trust. Make the secure path the easiest path.
