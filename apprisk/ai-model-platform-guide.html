Executive summary

The four layers of the AI stack and where the risk sits in each

The AI stack breaks into four layers: the models themselves, the hubs that distribute open-weight models, the cloud platforms that host and wrap models with enterprise controls, and the runtimes that serve models on your own infrastructure. Risk follows the layer. Closed models move risk to data handling by a third party. Open-weight models move risk to provenance and to your own hosting. Platforms concentrate risk in IAM and data connections. Runtimes concentrate risk in exposed endpoints and unmanaged use.

Key takeaways

  • Closed APIs (GPT, Claude, Gemini, Command, Grok): the main question is what data leaves your boundary, under which contract terms, retention setting, and region.
  • Open weights (Llama, Mistral, Qwen, DeepSeek, Gemma, Phi, Granite, Falcon, gpt-oss): the weights can run privately, but you inherit provenance, license, and patching duties.
  • Hugging Face is the main distribution channel for open weights. Treat it like a public package registry: pin, scan, and prefer safe formats.
  • Bedrock, Azure, Vertex give one IAM-governed door to many models. Misconfigured IAM, logging, and agent permissions are the main failure points.
  • Ollama and vLLM are common sources of shadow AI and unauthenticated model endpoints.

Decision questions for any model or platform

  1. Where does inference run, and in which jurisdiction?
  2. Is input or output data retained or used for training? Under which agreement?
  3. Where did the weights come from, and can you verify them?
  4. What tools, data sources, and credentials can the model or agent reach?
  5. What is logged, who can read the logs, and how long are they kept?
  6. What license and acceptable use terms apply to the model and its outputs?
Model versions and catalogs change monthly. This page describes families and platforms. Confirm current versions, terms, and regional availability on the linked provider pages before a decision.

Hugging Face deep dive

What the Hub hosts, model task types, the derivative tree, and file-format risk

Hugging Face Hub hosts models, datasets, and Spaces (hosted demo apps). Most open-weight models in this guide are published there, along with a much larger set of community fine-tunes, adapters, quantizations, and merges.

1. What the Hub hosts

2. Model types by task (Hub task taxonomy)

The Hub tags each model with a pipeline task. LLMs are only one branch. Embedding, vision, speech, and document models often enter the enterprise quietly through RAG pipelines and document processing.

3. Model variants and the provenance chain (Hub "model tree")

The Hub links derivatives back to a base model. Every step is a new publisher and a new trust decision. A quantized file from an unknown account is not the same artifact as the vendor's base model, even if the name matches.

4. File formats and load-time risk

Some formats are data only. Others run code when loaded. This chart rates the risk of loading an untrusted file, not the model's behavior.

5. Practical Hugging Face controls

Policy-level requirements

  • Models and datasets must come from approved publisher accounts (the vendor's official organization) unless a reviewer approves an exception.
  • Teams must record the model ID, commit hash, license, and source for every model used in production.
  • Teams must not load pickle-based weights or enable remote code from unapproved sources.
  • Personnel must not paste confidential data into public Spaces.

Implementation guidance

  • Pin downloads with revision=<commit hash>, not a branch name.
  • Prefer use_safetensors=True; keep trust_remote_code=False by default.
  • Review the Hub's file security scan results before use; add a pickle scanner such as ModelScan or picklescan in CI.
  • Mirror approved models to a private S3 bucket or internal registry and load only from there in production.
  • Read the model card for training data, limitations, and license (Llama, Gemma, and others have custom terms).
  • Track models in your SBOM or AIBOM alongside software dependencies.

Amazon Bedrock deep dive

Reference architecture, capabilities, and a right-sized control set

Amazon Bedrock is a managed AWS service that gives one API to many foundation models, plus building blocks for RAG, agents, guardrails, customization, and evaluation. It is a platform, not a model. AWS documentation lists 100+ foundation models from providers including Amazon, Anthropic, DeepSeek, Moonshot AI, MiniMax, OpenAI, and xAI, and the catalog changes frequently. AWS also added an OpenAI API-compatible endpoint (bedrock-mantle, powered by Project Mantle) alongside the native bedrock-runtime endpoint.

1. Reference architecture

2. Bedrock capabilities and their security meaning

CapabilityWhat it doesSecurity consideration
Model catalogOne API for many providers' models, served in AWS.Restrict which model IDs each role can call. Review each provider's EULA and acceptable use terms.
Data handlingAWS states prompts and outputs are not used to train base models or shared with model providers.Keep this claim tied to AWS documentation in vendor files. Fine-tuning data stays in your account.
Cross-Region inferenceInference profiles route requests across Regions within a geography (Geo) or worldwide (Global).Global routing can process data outside your home geography. Choose In-Region or Geo where residency matters.
GuardrailsContent filters, denied topics, word filters, PII detection and redaction, contextual grounding, prompt attack detection.Reduces, but does not eliminate, prompt injection and data leakage. Test with your own red-team prompts.
Knowledge BasesManaged RAG over S3 and other sources into a vector store.Retrieval does not enforce source-document permissions by default. Use metadata filters or separate knowledge bases per audience.
Agents and AgentCoreTool-calling agents, managed runtime, memory, identity, and tool gateway.Agent execution roles and Lambda tools are the blast radius. Scope each tool narrowly; require approval for destructive actions.
CustomizationFine-tuning, distillation, continued pretraining, custom model import.Training data governance; imported weights carry provenance risk. Encrypt with KMS.
Invocation loggingLogs full prompts and responses to CloudWatch Logs or S3.Off by default. When on, logs contain sensitive data: restrict access, encrypt, and set retention.
NetworkingVPC interface endpoints via PrivateLink.Combine with endpoint policies and aws:SourceVpce conditions to block calls from outside the VPC.

3. Right-sized Bedrock control set for a small team

Must have

  1. IAM policies that allow bedrock:InvokeModel* and bedrock:Converse* only on approved model and inference profile ARNs.
  2. An SCP in AWS Organizations that denies unapproved models and Regions.
  3. CloudTrail enabled for all Regions (already a SOC 2 baseline control).
  4. Model invocation logging to a KMS-encrypted S3 bucket with a defined retention period, if you need prompt-level evidence.
  5. A Guardrail attached to any customer-facing or agent flow.
  6. AWS Budgets alert on Bedrock spend.

Add as usage grows

  1. PrivateLink endpoint for bedrock-runtime with an endpoint policy.
  2. Separate AWS accounts for dev and prod Bedrock workloads.
  3. Per-tenant Knowledge Bases or metadata filtering for multi-tenant RAG.
  4. AWS Config rules or Security Hub checks for Bedrock settings.
  5. Scheduled evaluation jobs to detect quality regressions after model version changes.

Baseline controls

Governance and technical controls that apply to every entry

Governance

  • Keep an approved AI model and service inventory with owner, use case, data classification, and review date.
  • Review vendor terms for data retention, training use, subprocessors, and region before approval.
  • Map models into the vendor risk process the same way as other SaaS and open-source components.
  • Define which data classifications may be sent to which tier (closed API, cloud platform, self-hosted).

Technical

  • Route model access through a single gateway or cloud account so usage is logged and controllable.
  • Store API keys in AWS Secrets Manager or GitHub encrypted secrets; enable GitHub secret scanning.
  • Scope agent tools to least privilege and require human approval for irreversible actions.
  • Detect shadow AI: watch for Ollama (port 11434) and unknown model endpoints on endpoints and cloud networks.
  • Test against OWASP Top 10 for LLM Applications risks before release.
